# 掌机存档：从「一关就没」到「跟着这条聊天走」

> 这份文档讲 v5.8.0 的存档改造：为什么以前存的档会丢、现在怎么存、AI 回复完成那一声是怎么响起来的。
> 代码在 `pocket/src/pocket.10-save.js`（掌机侧）与 `src/87b-pocket-autosave.js`（宿主侧）。

## 一、原来错在哪

| 环节 | 以前 | 问题 |
| --- | --- | --- |
| 游戏内存档 | 写进核心符号 2 指向的 Flash 区（128KB + 8KB） | 这块内存只活在 iframe 里 |
| 关面板 / 换聊天 / 刷新 | iframe 被拆或页面重载 | 内存没了，档就没了 |
| 「导出存档」 | 把 128KB 拼成 Blob 下载 | 那是一次性文件，不是存档；玩家下次还得自己找回来 |
| 攻略里的说法 | 「跟着聊天记录走」 | 当时**并不成立**，只是句漂亮话 |

结论：以前只有「导出」，没有「存档」。这次补的是后者。

## 二、现在的三层触发

```
                     ┌──────────────────────────────┐
   游戏里按「保存」 → │ onSaveBufChanged（C 侧回调） │→ 500ms 后写盘
                     └──────────────────────────────┘
                     ┌──────────────────────────────┐
   什么也没发生     → │ 8 秒巡检一次，签名变了才写   │  ← 不靠回调也丢不了
                     └──────────────────────────────┘
                     ┌──────────────────────────────┐
   AI 写完回复      → │ 宿主发 moon-host:autosave    │→ 立刻写盘 + 屏内提示
                     └──────────────────────────────┘
```

三条路都走同一个 `savWrite()`：抓快照 → 算签名 → 没变就不写 → 压缩 → 存进 `moon-pocket:cart-save:<卡带指纹>`。

## 三、压缩：139264 字节 → 491 字节

| 数据 | 算法 | 压缩后 | base64 |
| --- | --- | --- | --- |
| 空档（全 0xFF，从没存过） | deflate-raw | 151 B | 约 200 字符 |
| 有内容的档（8 段数据块 + 大量空区） | deflate-raw | 491 B | 656 字符 |
| 同上，浏览器不支持 deflate-raw | 字节级 RLE | 约 1 KB | 约 1.4 KB |
| 纯随机数据（最坏情况） | 不压缩（`k:"n"`） | 139264 B | 约 18.6 万字符 |

三条兜底，最后一条有硬上限：落盘 JSON 超过 20 万字符就**拒绝写并说明原因**，不硬塞进 `chatMetadata`（宿主侧还有 256KB 的保护）。

为什么能压这么狠：GBA Flash 存档里绝大部分是 0xFF 空区，宝可梦真正写数据的地方只有几十 KB。

## 四、开机顺序（这个反了就白存）

```js
M._emuLoadROM(buf.length);        // ← 这一步会把存档区清掉
await savRestoreToCore();         // ← 所以必须在它之后写回
M._emuResetCpu();                 // ← 复位之后，游戏从「卡带里有存档」开机
```

写反了就是「存了但读不到」，而且现象很像「存档坏了」，很难查。代码里这段有注释钉着。

## 五、消息协议（掌机 ↔ 宿主）

掌机在 sandbox iframe 里（opaque origin），碰不到酒馆的任何东西，所以全靠 postMessage：

| 方向 | type | 说明 |
| --- | --- | --- |
| 掌机 → 宿主 | `moon-pocket:ready` | iframe 起来了，请求还存档 |
| 掌机 → 宿主 | `moon-pocket:playing` | **真的跑起卡带了**（不是只打开面板） |
| 掌机 → 宿主 | `moon-pocket:persist` | 整包键值（含压缩后的存档），宿主写 `chatMetadata` |
| 掌机 → 宿主 | `moon-pocket:saved` | 这一次存的结果（ok / 字节数 / 卡带代号） |
| 掌机 → 宿主 | `moon-pocket:chime-set` | 玩家点了静音 / 打开 |
| 宿主 → 掌机 | `moon-host:restore` | 把整包还回去 |
| 宿主 → 掌机 | `moon-host:autosave` | AI 回完了，现在存一次 |
| 宿主 → 掌机 | `moon-host:chime-state` | 提示音该开还是关 |

`moon-pocket:playing` 是这套协议的关键：没有它，宿主分不清「玩家在玩」和「玩家只是看了一眼面板」。

## 六、那一声提示音

```js
[[783.99, 0], [1046.5, 0.13]]   // G5 → C6，第二个音晚 130ms
  .sine → gain(0.07, 起 30ms / 衰减 850ms) → lowpass(2200Hz) → destination
```

- 两个正弦音、一个低通：听感像门铃，不像警报；音量 0.07，比酒馆自己的通知音还轻。
- **AudioContext 必须在用户手势里创建**（点开面板那一下），否则等到 AI 回复完再建，会挂在 `suspended`，一点声都没有。这条也写进了注释。
- 关掉只影响声音，不影响存档。开关存在酒馆的 `localStorage`（`moon_phase_pocket_chime_v1`），换聊天还是这个选择；掌机上那行 `提示音 · 开/关` 跟着同步。

## 七、去抖：为什么不会响两次

酒馆会先后发 `generation_ended` 和 `message_received`，两者相差几十毫秒。`pocketAfterAiReply()` 里做了 1.5 秒窗口，只处理第一次。

## 八、记的是真实楼层，不是猜的

存完宿主从 `ctx.chat` 里往前找最后一条 `is_user === false` 的消息，把楼层、`send_date`、前 60 字摘要记进 `chatMetadata`：

```json
{
  "at": 1794599358785,
  "floor": 1,
  "msgId": 1730000000000,
  "snippet": "好，路上小心。店里我看着。",
  "code": "BPEE",
  "bytes": 491,
  "reason": "ai-reply",
  "ok": true
}
```

以后想知道「这局是第几楼那轮回复时存的」，查得到。

## 十、测试

| 脚本 | 覆盖 | 结果 |
| --- | --- | --- |
| `pocket/tools/verify-save.mjs` | 压缩往返、写盘读盘、不重复写、空档不写、换卡带不串档、坏档不崩 | 18/18 |
| `scripts/verify-pocket-autosave.mjs` | 什么时候该响、静音仍存档、楼层取自真实聊天、拆掉 iframe 后不响 | 21/21 |

## 十一、还做不到的

- **换设备**：存档挂在 `chatMetadata` 里，跟着聊天记录走，所以换设备只要聊天同步过去就还在；但它不是云盘，聊天记录本身丢了就没了。
- **多份存档位**：现在每张卡带一个槽，新的覆盖旧的。要「存三份随时回到某一份」，得再加一层槽位管理。
- **游戏内多存档**：那是卡带自己的事（宝可梦能吃多个存档位），掌机只负责整块 Flash 的搬运，不解析里面的结构。
